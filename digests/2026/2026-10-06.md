### [Claude Code’s /effort dial, and when the tokens earn their keep](https://claude.dev/blog/spending-your-effort/)

Anthropic engineer Thariq Shihipar’s field guide to Claude Code’s `/effort` settings is the useful half of this week’s coding-agent mail, separate from the mods walkthrough already covered on Sunday. Effort is how much verification, edge-case hunting, and independent judgment Opus 5.5 or Fable 5.1 is allowed to spend without breaking the prompt cache. On Terminal-Bench 3.0 the highest setting burned roughly three times the tokens of the lowest, and the payoff was uneven: security pass rates jumped from 64% to 87% and hardware from 34% to 75%, while rulebook-style operations work barely moved. Max is for autonomous hard problems; low is for sketching while you stay in the loop.

### [Lost in the middle: why your agent ignores the constraint in paragraph 40](https://blog.bytebytego.com/p/the-llm-blindspot-why-models-forget)

ByteByteGo’s explainer on the “lost in the middle” effect is the agent-context piece of the day. The 2023/24 paper’s U-shaped accuracy curve — primacy plus recency — still shows up when the critical fact sits in the middle of a long prompt even though it is inside the window. Causal masking gives early tokens more influence paths through the layers; tokens near the end sit next to the question the model is about to answer; the middle gets neither advantage. Bigger windows raise capacity, not uniform reliability (RULER shows length degradation, though it is not position-controlled). Mitigations that matter for harnesses: state critical constraints up front, tag documents clearly, put the question after the sources, prune instead of arbitrary token caps, and treat RAG as a smaller haystack that can still hide the needle. If your coding agent deleted logs at day 30 when the policy said 37, position is a suspect before “the model can’t count.”

## Agent memory

### [DyadMem: A Long-Term Memory Benchmark of How Agents Work with Users](https://arxiv.org/abs/2610.03020)

Most memory benchmarks ask whether an assistant remembers facts about you. DyadMem asks something subtler: does the agent remember how it should work *with* you as your shared history builds up? The authors call this User-conditioned Relational Agent Memory and annotate it alongside ordinary user memory across 3,065 episodes, nearly 51,000 sessions and 61,000 questions, with gold labels for when a memory should be captured, updated and recalled. The gap they find is stark. When models are handed the correct memories, all 20 tested (16 open-weight, four proprietary) answer well, but accuracy falls sharply once they have to run the whole pipeline themselves. Even frontier models miss things they should have captured, recall only part of what they need, and sometimes delete memories they should have kept, which suggests the bottleneck is memory upkeep rather than reasoning.

### [APDMem: Agent-Controlled Progressive Disclosure for Query-Adaptive Long-Term Memory](https://arxiv.org/abs/2610.02472)

APDMem borrows progressive disclosure, a familiar interface-design idea, and applies it to an assistant’s memory. Conversation history is stored in four layers of increasing detail: thematic summaries, personal key facts, turn-level evidence notes and finally the raw messages. A controller starts at the top and only drills down when a question demands it, so a simple lookup can stop early while a temporal or multi-hop question pulls up the exact turns it needs. A note synthesizer then organizes the retrieved evidence, ordering events and flagging contradictions before the model answers. On LongMemEval the system performs strongly while reading only about 8% of the stored conversations.

### [Decoupling Memory from Context: Structured Memory for Token-Efficient Test-Time Continual Learning](https://arxiv.org/abs/2610.02687)

Agents that learn from experience usually do it by appending lessons to a shared context, which works until the context gets expensive, hits the window limit and starts to hurt performance. This paper reframes a memory update as an optimization step over the model’s context, which gives memory design a more principled footing, and then proposes GraphMemory, a lightweight graph that accumulates, refines and links reusable strategies. For each query only the relevant subgraph is retrieved, so the amount of memory the model sees stays constant however many examples it has processed. The result is competitive task performance with roughly 81–85% fewer tokens spent building memory than the baselines.

### [Interpreting at Write Time: A Policy Ablation for Multi-Goal Agent Memory](https://arxiv.org/abs/2610.02897)

A long-running assistant can’t keep everything, so it summarizes, and every summary is a bet about what will matter later. This short, sharply argued paper asks what that summary should be written *for* when the assistant serves several standing goals at once. It compares three policies with the read step held fixed: a neutral summary, one summary covering every goal, and a separate summary per goal. Different goals turn out to want different things, since summaries written for different goals overlap less than a summary overlaps a rewrite of itself. Per-goal summaries win on relevance, completeness and accuracy. The surprise is that the all-goals summary loses even to the neutral one written on a fraction of the budget, so interpreting at write time helps only for the goal that eventually asks.

### [Lost in the Request: How Communication Variation Disrupts Retrieval and Action in Email Agents](https://arxiv.org/abs/2610.02627)

An email assistant shouldn’t do less work just because you phrased a request politely or indirectly, yet most benchmarks test each task with a single canonical wording. This study keeps the task, the evidence and the expected outcome fixed and varies only the communication style and English dialect, across a RAG pipeline and two tool-using agents. Indirect requests hurt all three systems, and formal ones hurt both agents. The causes differ, though. Verbose requests mostly confuse a lexical retriever, while indirect and dialect variants still fail even when the right email is found. In the agentic runs, the typical failure is quietly skipping required actions rather than doing something unsupported, which a pass/fail check on the final reply can easily miss.

### [How To Train Your World Model: Fine-tuning vs RAG for LM-based World Modeling](https://arxiv.org/abs/2610.02542)

If a language model is going to act as an agent’s world model, predicting what happens after each action, should you fine-tune it on experience or let it retrieve past transitions? Across five embodied, web and social environments, fine-tuning usually wins, giving higher agent rewards in 15 of 20 settings, though RAG learns more from less data while fine-tuning benefits more as experience scales. The authors dig into why retrieval falls short, using counterfactual interventions to show that retrievers keep surfacing the wrong past transitions, and find that hierarchical query reformulation helps. Their final system is a hybrid that learns the core dynamics in its weights and leans on an actively maintained memory for the rest, and it beats both approaches across environments and models.

## Agent harness

### [Sentry: Learning to Recover from LLM Agent Failures at Test Time](https://arxiv.org/abs/2610.02994)

A popular way to make agents more reliable is to keep a growing playbook of lessons from past failures in the prompt. Sentry’s authors find that this backfires: lessons about a specific failure misfire when that failure isn’t happening, and pruning them from the playbook actually improves results. Their answer is a failure-management layer that runs alongside the agent and stays out of its context. When it detects something going wrong, such as an invalid tool call or a loop, it retrieves matching lessons to guide recovery, checks without access to task rewards whether the agent recovered, and only then saves a new lesson. Sentry beats the best runtime-intervention baseline by 37% on average and the best context-evolution baseline by 39%. Notably, showing the agent the full playbook hurt performance even when the relevant lessons were available on demand.

### [VERSE: Verified Self-Evolving Optimizer for Agent Harnesses](https://arxiv.org/abs/2610.02616)

Harness-optimization systems rewrite an agent’s prompts, tools and workflow, but the optimizer itself usually stays frozen. VERSE lets the optimizer improve its own tools and procedures as well, with one crucial condition. In a controlled study, optimizer self-evolution didn’t help without execution-based verification but gave the best results once verification was available. So VERSE lets the optimizer test draft edits, replay failures and perturb suspect steps before submitting a change, and track fixes and regressions across rounds, all while model weights stay fixed. Along the way the optimizers built their own tools for failure analysis and training audits. VERSE improved all four harness optimizers tested on held-out SWE-rebench tasks, reaching 42.3% against a best baseline of 39.2%, and did even better on newer out-of-distribution tasks in five languages, with 37.7% against 29.3%.

### [HASTE: Evolving Agent Harnesses Against Emerging Attacks Using Sparse Evidence](https://arxiv.org/abs/2610.02920)

New attacks on agents often appear as little more than a paragraph in a threat report or a handful of examples in a preprint, far too little to harden a harness by hand before the next one arrives. HASTE automates that work with a multi-agent loop in which one side writes safety specifications that drive harness updates and the other generates fresh attack cases to probe what the update still misses. Feeding the results back into both sides lets the harness generalize beyond the few examples it started from. Across several backbone models, attack types and kinds of evidence, the approach consistently lowers attack success rates without hurting performance on benign tasks.

### [LEAP: Learning Efficient Action Proposals For LLM Agents](https://arxiv.org/abs/2610.02670)

Agents are slow because each step must finish before the next can start, and speculative decoding only speeds up the reasoning tokens, not the action choices. Recent work drafts actions with an off-the-shelf model for the main model to verify, but large drafters are slow and small ones rarely guess right. LEAP starts with a latency model that weighs what a speculative round saves against the cost of drafting, verification and tool execution, then follows its own advice: keep the drafter tiny and train it on the target model’s own action sequences. A 0.6B drafter agrees with the target on most decisions and makes agents up to 60% faster end to end with no systematic loss in task success. It can also be trained online with no prior trace collection, which makes it practical to deploy.

### [Lightweight, Rubric-Guided Trajectory Evaluation for Production AI Agents](https://arxiv.org/abs/2610.03315)

Reading full agent traces with a judge model is the obvious way to find out where agents go wrong, and it becomes very expensive when traces are long and production traffic never stops. LiteTrajEval builds compact domain-specific rule profiles offline, then flags heuristic failure signals in each trajectory, compresses it to a fixed token budget and makes a single rubric-guided judge call that returns a structured diagnosis. On Magentic-One-style and τ-bench-style datasets, it matches human failure localization 20–35 points better than AgentRx on Magentic-One and up to 23 points better on τ-retail, while costing about six times less and running more than eight times faster. It already runs on the authors’ enterprise agent platform.

### [Engineering Sustainable Agents: A Systematic Comparison of Agentic LLMs for Developer Workflows](https://arxiv.org/abs/2610.03010)

Multi-agent setups for software engineering are fashionable, and this study puts a price on them. Across code generation, technical-debt detection, vulnerability detection, log parsing and log analysis, the authors compare everything from a single non-agentic query to full multi-agent workflows, using six open-weight models, two prompting strategies and three hardware platforms. On average, multi-agent designs used 6.4 times the energy and took 6.1 times as long as the simple baseline, and one task-hardware pair ran up to 160 times slower. The accuracy gains were small and task-specific, with vulnerability detection the main exception. Lightweight single-query and single-agent setups took 59 of the 66 spots on the accuracy-versus-cost Pareto front.

## LLM security

### [Securing Computer-Use Agents Against Branch Steering Attacks](https://arxiv.org/abs/2610.03089)

The Dual-LLM pattern, where a planner model fixes the execution path before a quarantined model ever touches untrusted content, is one of the few prompt-injection defenses with formal guarantees. Those guarantees weaken in graphical interfaces, where a computer-use agent’s plan has to branch on whatever appears on screen. That opens the door to branch steering, in which an attacker doesn’t inject instructions at all but crafts page content that pushes the agent down a harmful branch the planner already approved. On the new 101-task STEER-Bench, such attacks succeed 94.4% of the time against standard agents and 89.5% against plain Dual-LLM agents. The proposed COBRA architecture pairs trusted branching plans with up-front limits on the parameters and destinations each branch can use, cutting attack success to zero while keeping 97% of benign utility.

### [MLCommons Jailbreak Benchmark v1.0](https://arxiv.org/abs/2610.02827)

MLCommons has turned jailbreak testing into a full benchmarking pipeline. It covers how systems and attacks are selected, paired baseline and adversarial runs, human annotation, evaluator calibration, grading, and even how results are disclosed relative to their risk. Version 1.0 tests eight open-weight systems with 264 seed prompts across eleven hazard categories, using attacks drawn from the MLCommons Jailbreak Taxonomy and judging responses against the AILuminate standard. The headline metric, the Resilience Gap, measures how much safety drops under attack: unsafe responses rose from 11.08% to 18.65% on average, a gap of 7.57 points, with large swings by attack type and hazard. The report also takes evaluator reliability and measurement error seriously, which is rare among jailbreak leaderboards.

### [CorrectGuard: Eyes-Off Correctness Estimation for Black-Box Security Guardrails](https://arxiv.org/abs/2610.03470)

Privacy rules often mean nobody may look at the production inputs a guardrail is screening, so how do you know whether it is working? CorrectGuard trains a separate evaluator, using only labeled data that people are allowed to see, to predict whether a black-box guardrail’s decision on hidden traffic is correct. It works both when humans can’t inspect the inputs and when even models can’t, which the authors handle with privacy-preserving fingerprints. Across 13 datasets covering harmful content, jailbreaks, prompt injection and extraction, in-context-learning evaluators improved error detection by up to 25 points of macro accuracy, though results varied a lot from one guardrail to another. Those correctness scores can also rank decisions or trigger abstention, roughly halving AURC risk without any access to the guardrail’s internals.

### [Containing the Autonomous Operator: A Defense-in-Depth Framework and Reference Architecture for Securing AI Agents on Kubernetes](https://arxiv.org/abs/2610.02861)

Once an agent reads logs, tickets and tool descriptions and can also change a production Kubernetes cluster, the line between data and control disappears, because anything it reads can steer what it does. This paper’s starting rule is that the model is never a security boundary, so every guarantee must hold even if prompt injection compromises the agent completely. It lays out a ten-class threat taxonomy aligned with OWASP’s agentic guidance and seven defensive layers built from standard tools: workload identity, RBAC and admission policy, gVisor or Kata sandboxing, FQDN-aware egress rules, an MCP gateway that enforces policy on tool arguments, and eBPF runtime enforcement. It also includes concrete bindings for EKS, AKS and GKE. The authors are upfront that they report no measured attack-success or overhead numbers yet, only a coverage matrix, four attack walkthroughs and a plan for validating the design.

### [Persona Guardrail: A Production-Grade Defense Framework for Agentic Systems](https://arxiv.org/abs/2610.03434)

Most runtime guardrails hunt for specific attacks such as prompt injection, but a customer-facing agent also needs to refuse things that are merely outside its job. Persona Guardrail checks both inputs and outputs against semantic allow and block lists that define what the agent is for. The authors also release PAGE, a benchmark of benign, adversarial and out-of-domain conversations covering both user and agent turns. Compared with a generic LLM guardrail, it raises overall accuracy from 85.7% to 95.9%, out-of-domain detection from 57.3% to 93.5%, and cuts wrongly approved requests from 25% to 4.7%. The system is already in production, where it stays within its latency budget while keeping both false blocks and false allows low.

### [Bounded Reachability & Jailbreak Detection via Contraction-Constrained State Space Models](https://arxiv.org/abs/2610.02853)

Safety heads, small classifiers that flag harmful prompts before generation, are usually judged on empirical accuracy alone. This paper asks when an SSM-based head can be *certified* to give the same verdict for every input within a perturbation bound, and finds a clean answer: the state transition matrix must be a contraction, with infinity norm below one. When that holds, exact interval bound propagation works. When it doesn’t, the bounds blow up exponentially with sequence length and certification becomes impossible. Enforcing contraction during training raised the certified fraction on toxic-comment data from 41% to 59%, with a sharp phase transition right at the boundary the theory predicts. In an honest twist, a plain logistic regression on Mamba embeddings detects jailbreaks just as well, so the head’s real value is the formal guarantee, not better detection.

## Engineering blogs

### [Quoting Felix Rieseberg](https://simonwillison.net/2026/Oct/5/felix-rieseberg/)

Anthropic’s Felix Rieseberg explains a quiet but significant change in how Claude Cowork runs, and Simon Willison flags it. The original Cowork ran inference in the cloud but executed tool calls inside an Anthropic VM shipped to your own computer, mapping in only the data you added to a session, for capability, safety and security reasons. Users liked the results but not the disk, battery and performance cost, or the fact that closing the laptop stopped the work. In the new design both inference and the VM run in the cloud, and each session gets its own isolated sandbox. The desktop app now acts as a tool that handles file access when the remote VM needs something from your machine. That makes phone access and long-running sessions possible, and it moves the trust boundary in a way that agent builders will want to note.

### [Qwen3.8 27B addition in words](https://simonwillison.net/2026/Oct/4/qwen38-addition-in-words/)

Inspired by a two-year-old GPT-4o experiment that resurfaced on Bluesky, Simon Willison had a Codex Remote session rerun it on a DGX Spark: can a local Qwen3.8-27B add two integers and give the exact answer spelled out in English words? With reasoning off, across 5,070 cases, the model followed the format 96% of the time but got the number right only 23.6% of the time, falling from 97% on one- to three-digit operands to just 6.4% at ten to thirteen digits. With reasoning on, it got 167 of 169 one-shot attempts right. The traces show it laboriously lining up digits and carrying ones, which is a neat demonstration that reasoning mode is really buying scratch space for the model.
