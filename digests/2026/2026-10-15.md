## Agent memory

### [MemForm: Benchmarking Memory Formation Poisoning in LLM Agents](https://arxiv.org/abs/2610.14431)

Most work on memory poisoning asks how bad data gets into an agent's long-term memory; MemForm asks a quieter question about the machinery that decides what gets written down. The benchmark defines five formation interfaces, covering the content of a memory, its supporting evidence, its scope, which experiences are selected for retention, and the order in which they are consolidated, and it pairs clean and poisoned runs for each. Across six models the agents proved susceptible at every one of them. The unsettling finding is that authentic, successful experiences are no guarantee of good behavior later: simply reordering how identical experiences are consolidated can change what the agent does, and the defenses tested only partly helped.

### [Can Agents Forget When Asked? A Benchmark for Memory Unlearning in LLM Agents](https://arxiv.org/abs/2610.18052)

As agents accumulate personal details over months of use, users will increasingly ask them to forget a sensitive fact, and a decent memory system should remove exactly that and nothing more. Bemula, billed as the first benchmark for this, contains 50 multi-session dialogues, 135 forget requests of six types and 1,742 test questions, each dialogue paired with a control version so that only systems that actually stored a fact can earn credit for forgetting it. The results are blunt: across six mainstream memory systems and three backbone models, none passed more than 1.5% of forget requests end to end. Most either left the information easy to extract or erased far more than was asked.

### [Recall What Is Missing: Composing Evidence from Long-Term Agent Memory](https://arxiv.org/abs/2610.15642)

When an agent has only a handful of context slots to spend on memories, retrieving the ten most relevant ones often means paying for the same fact ten times while a complementary clue stays behind. This paper reframes the read step as evidence composition, valuing each memory by what it adds beyond what has already been selected. The method, MemPursuit, needs no language model at retrieval time: it reuses the embeddings the retriever already computed and treats the residual of a sparse reconstruction of the query as a proxy for what is still missing. On LoCoMo it lifts end-to-end accuracy by 7.2 points at top-10 and 5.5 at top-20, while reranking runs about 33 times faster than a batched BGE cross-encoder.

### [Memory Echo in Single-Agent Long-Term Memory: Lifecycle Evaluation and Provenance-Guided Mitigation](https://arxiv.org/abs/2610.17763)

Borrowing from the psychology of repeated exposure, the authors point to a failure that grows out of ordinary memory use: when an agent keeps retrieving a claim and writing it back, one historical statement can end up occupying several retrieval slots and steering current answers with no new evidence behind it. They call the effect Memory Echo and build MEchoBench to measure how it emerges, resists correction and persists. Their remedy tracks provenance, keeping one representative per source family, letting old records into the context only if corrections have been verified, and anchoring final answers in authoritative evidence. In paired replay it raised accuracy from 0.825 to 0.920 with one model and from 0.782 to 0.916 with another.

### [Reliable Memory from Unstable Growth: Curating Self-Written Agent Playbooks with Randomized Experiments](https://arxiv.org/abs/2610.18427)

Systems such as ACE and Dynamic Cheatsheet let an agent write lessons after each task and reread them as a playbook, but this paper shows that letting the agent decide which lessons to keep makes results erratic: the same procedure can produce a playbook that lands almost 70 points below having no playbook at all. The fix borrows from clinical trials. Randomized Block Curation groups related lessons into blocks, switches each block on or off at random across practice tasks, and reads the resulting gap in success as that block's true effect, then serves whichever curated, full or empty playbook scores best on fresh episodes. Average success reaches 66.9, compared with 55.5 for the whole playbook and 53.8 when the agent judges for itself.

### [Pack Light, CarryOn: Building Object-Oriented Context for Long-Horizon Agents](https://arxiv.org/abs/2610.18784)

Long-running agents tend to drag along a growing transcript of how they got somewhere, even though what they need next is the progress itself. CarryOn flips the organizing principle of context: instead of compressing the history, it builds the prompt around reusable task objects, which it calls continuation carriers, plus the relevant execution context and a short live tail of recent steps. The hard part is keeping those objects trustworthy after the history behind them is retired, so each time the context is folded the runtime revises only the records affected by new evidence and carries the rest forward. On OSWorld 2.0 and BrowseComp-Plus it improves results by 5.8% and 7.0% while cutting token use by 51.9% and 22.9%.

### [Many Steps into One: Reasoning Contraction and the Limits of Safe Memory Reuse for LLM Agents](https://arxiv.org/abs/2610.17544)

Thought templates, skill libraries and caches all promise to collapse many reasoning steps into one, but the authors argue that a contracted memory is dangerous in a specific way: it keeps saving effort until the underlying facts change and then answers wrongly without any warning. Most systems decide whether to trust a memory by counting its successes and failures, and the paper proves that such counters are poor change detectors, sometimes never noticing a partial change at all. In experiments on edited facts, counters in the style of ExpeL and ACE served 7 to 13.5 times more stale answers than certified memories, and 35 to 73 times more on code tasks with an exact verifier. Their recipe restarts a memory's certificate whenever facts change.

## Agent harnesses and skills

### [StateHarness: Maintaining Evolving Project State for Long-Horizon Coding Agents](https://arxiv.org/abs/2610.17616)

A coding agent working across a large repository tends to lose the thread, because its picture of what it has learned, changed and left unfinished is scattered through an ever-longer history. StateHarness is a runtime layer that keeps that picture explicit without touching model weights: the agent logs its current problem and hypothesis, key findings and decisions, discovered repository relationships and open work, while the runtime nudges it to update the record and to search for callers, tests and documentation a change might affect. On RefactorBench, full-chain completion rose from 29.4% to 35.3%, and on five long-horizon software tasks mean reward went from 0.427 to 0.576. The catch is that pass-to-pass regressions increased on ChainSWE, even as the bug-fix rate improved.

### [Self-Evolving Agent Harness](https://arxiv.org/abs/2610.18813)

This 66-page survey and framework treats the harness, meaning the prompts, memory, workflows and code wrapped around a frozen model, as the thing that learns. It separates what gets updated from how revisions are proposed and admitted, and it distinguishes changes to interpreted state from edits to tools, code and plugin composition. The more unusual contribution is a theory of when it is safe to keep a revision: using continual PAC-learning, the authors derive a generalization bound, a retention bound tied to historical regression budgets, and an admission rule that relies on fresh, independent validation data. The practical message is that persistent harness changes need continual validation and separate safeguards for runtime privileges and consequential actions.

### [TurnCost: Turns, Not Observations: Cache-Aware Loop Engineering for Coding Agents](https://arxiv.org/abs/2610.15093)

Much of the effort to make coding agents cheaper goes into compressing bulky tool output, but a study of 600 public trajectories suggests that is aiming at the wrong target. Median observations hold only 118 to 286 tokens, the giant build logs that motivate compression sit near the 99th percentile, and 98.6% of input tokens come from a prefix cache, so flat input pricing overstates loop cost by roughly seven times. What really drives cost is the number of turns, which explains 84% of the variance in log trajectory cost, against 4% for mean observation size. Routing turns to a cheaper model raised cost in half the settings, and the authors release TurnCost for rescoring trajectories under other policies.

### [Harness^2: Recursive Agent Harnessing for an Open World](https://arxiv.org/abs/2610.14224)

Self-improving harnesses work well when a verifier can say whether an edit helped, but open-world tasks rarely come with one. Harness^2 tackles that with two layers of recursion. At the task level, a contrastive Propose-Probe-Compose step refines the harness for the problem at hand without ground truth, and can be scaled through parallel or sequential attempts. At the harness level, the experience from those edits is distilled into a continual-improvement harness so future tasks start from a better place. Across three professional benchmarks and four model-harness setups, a single step improved GLM-5 and Gemini 3.5 Flash by up to 11.5 points on WorkBuddy-Bench, 4.5 on JobBench and 11.8 on LAB, with gains growing as the recursion budget increased.

### [Lost in Implicit Routing: How LLM Agents Fail to Load Relevant Skills at Scale](https://arxiv.org/abs/2610.18522)

Agent skills, the on-demand instruction packs that tools like Claude Code can open, quietly assume the model will pick the right one from a list of descriptions. This paper tests that by keeping SkillsBench tasks and their golden skills fixed while piling on irrelevant skills, and finds what it calls routing collapse: with 1,000 distractors, recall of the needed skill falls from 73.6% to 27.4% and agents load no skill at all 51.6% of the time. Explicit selection from the same library keeps recall at 73.9%, and hiding only the distractors' descriptions largely restores loading, which points to interference from the metadata itself. Preselecting skills outside the agent loop emerges as the practical remedy.

### [AM-Bench: Understanding Agents under Task Underspecification across Models and Harnesses](https://arxiv.org/abs/2610.18090)

Real requests are rarely complete, yet agent benchmarks usually hand over a fully specified task. AM-Bench takes 48 Terminal-Bench-derived tasks and gives each a complete reference plus six degraded versions with ambiguous or missing goals, context or constraints, then runs every pairing of five models and four harnesses, 20,160 runs in all. Missing information hurts more than ambiguity, and it hurts in different ways: absent goals block completion, absent context inflates token use, and absent constraints erode compliance without necessarily stopping the agent from finishing. Rankings also shift with the model-harness pairing and the metric used, and asking clarifying questions could recover unfinished work but would leave most constraint violations untouched.

### [Cortex: Measurement-Gated Evolution and Pruning of Coding-Agent Skills and Rules](https://arxiv.org/abs/2610.14216)

Developers keep patching their coding agent's instruction files, the project notes, skills and auto-loaded rules, each time it makes a mistake, but one successful run proves little because the same agent can fail the next time. Cortex treats those edits as hypotheses: it turns corrections from real sessions into replayable tasks, writes one skill or rule at a time, and keeps it only if repeated runs with and without it show a net gain and no regression, applying the same test before deleting old text. Tried with Claude Haiku 4.5, rules did most of the work, while skills helped only when offered alongside the files a task touched. The authors candidly note that it proves Cortex keeps no unused text, not that it detects harm.

## AI security

### [MetaCascade: End-to-End Attacks on Agent Skills via Metadata-Only Poisoning](https://arxiv.org/abs/2610.14836)

Research on malicious agent skills has mostly looked at the harm done after a skill runs, but MetaCascade focuses on the earlier moment when an agent decides which skill to use at all. Because an agent first retrieves candidates from skill documentation and then chooses using their metadata, an attacker who controls only that metadata can influence the entire chain. The framework generates many malicious candidates, then uses black-box feedback from competing skills to iteratively tune the metadata until the target is chosen. Tested on four datasets with the Hermes and OpenClaw agents, it beat the strongest baselines by an average of 35.5 percentage points in attack success, and by 34.7 points even when four defenses were switched on.

### [Encrypted Skills Can Become New Security Exploits If AI Agents Know How to Decipher](https://arxiv.org/abs/2610.18262)

A malicious instruction doesn't have to be readable to be dangerous, as long as the agent can decode it. Ciphered Skill Injection hides instructions in third-party skill files using Caesar-style encodings, including layered variants, and relies on the model to decipher and then obey them. Across eight models and 139 injection-task pairs, the two variants reached attack success rates of up to 47.5% and 40.3% with shortened skills. Decoding alone didn't guarantee success, and layering helped on some models and hurt on others, but the more worrying result is on the defensive side: the skill scanners tested rarely flagged the injected files, because the payload only becomes an instruction once the agent has done the decoding.

### [TRAP: Tool-result Replay Attack for Probing Misbinding in LLM Agents](https://arxiv.org/abs/2610.16333)

This paper identifies a failure that involves no forged data at all: a genuine, unmodified tool result is simply consumed in the wrong context. As results persist in caches, recovery paths and shared runtime state, an agent can be handed a real output that belongs to a different task and act on it unsafely, a problem the authors call tool-result misbinding. Their ReplayBench covers 19 agent scenarios, four failure properties and three replay mechanisms, and across eight models and three agent frameworks the mean final-state error rate under cross-task replay was 0.649. The errors trace to the model's action generation rather than retrieval, and they stay high even when results are stale, which argues for explicit contextual binding in agent runtimes.

### [BrowseSafe++: Benchmarking Prompt Injection Detection Across Web Contexts, Languages, and Browser Views](https://arxiv.org/abs/2610.17457)

Browser agents read whatever a webpage says, which makes hidden instructions on that page a standing threat. BrowseSafe++ expands an earlier benchmark to 38,675 page pairs, most with injections observed in the wild, each paired with a clean copy and offered as HTML, Markdown, an accessibility tree and a screenshot, spanning twelve site types and 24 attack types. The authors use it to train two compact 0.8-billion-parameter detectors, one for text and one for screenshots, which beat a detector built on frontier models while keeping false positives and cost low. The sobering counterpoint is BrowseSafe-Adapt: injections that succeed on only a few percent of tasks when replayed directly reach up to 95.41% once revised using the browser agent's feedback.

### [Names Are Not Objects: Object-Bound Confinement for Compromised AI Coding Agents](https://arxiv.org/abs/2610.14488)

Many exploits against deployed coding agents share a quiet root cause: a safety check approves a name, such as a path, an argument list or a directory, and a later step resolves that name to something else, like the file behind a symlink or a repository git finds on its own. Zero-Trust Agent Cells assume the agent is already compromised and run it in a kernel sandbox whose only route to files, programs and the network is a broker, which resolves each request to the actual object, decides on that object and verifies it again at use. Against 74 attacks, a tool allowlist lost 66, an allowlist plus a typical command sandbox lost 56, and ZTAC lost 2, with a 3.2k-line Rust prototype adding about 4 ms per brokered request.

### [Kairos: Transactional Security Enforcement at the System Boundary for LLM Agents](https://arxiv.org/abs/2610.18457)

The trouble with stopping prompt injection at the level of individual actions is that the first step of an attack often looks just like legitimate work; what gives it away appears later in the trace. Kairos is a reference monitor that sits at the isolation boundary of an unmodified agent, where tool calls, shell commands and scripts the agent writes all show up as ordinary file and network operations. A declarative policy of trusted sources settles most effects immediately and defers the rest, holding them while the agent keeps working speculatively until a decision oracle, either a language model or a person, releases or refuses each one. On AgentDojo it cut attack success from 47.0% to 2.7% with benign utility essentially intact.

### [Welcome to the Age of Agent Ads: Using On-Policy Attacks to Steer Agentic Decisions](https://arxiv.org/abs/2610.17195)

As people hand shopping, travel and job searches to AI agents, sellers gain a reason to nudge those agents, and this paper shows a way to do it without ever asking a model to misbehave. The attack first adds a perfectly truthful negation to a product listing, such as saying it does not contain a made-up ingredient, which prompts the agent to search for the unfamiliar term. Planted websites then link that invented ingredient to health harms, and the safety-trained agent, doing exactly what it was taught, marks down every option lacking the reassurance. Evaluated on four real listing datasets, some frontier models were exposed, letting an adversary penalize competitors without breaking platform rules.

### [Tree Appreciator](https://simonwillison.net/2026/Oct/14/tree-appreciator/)

Simon Willison's latest small game experiment with Claude was built entirely from a single prompt in the ordinary Claude iPhone app, in chat mode rather than Claude Code. He asked Opus 5.5 Max for a three.js game called Tree Appreciator, in which you look at two algorithmically generated trees and appreciate their differences, and told it to think hard about making the game fun and beautiful. Somewhat embarrassingly given his recent talk, he finds that simply telling Opus 5.5 to make sure it is fun works uncomfortably well. After crunching for three hours and seven minutes it returned a cosy spot-the-difference game with music, animation and achievements that he found quite compelling to play.
