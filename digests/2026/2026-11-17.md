## Always-on and personal agents

### [How Claude Duet wants to finish your to-do list](https://www.thedeepview.com/articles/how-claude-duet-wants-to-finish-your-to-do-list)

The Deep View spent a month with Claude Duet, Anthropic's always-on agent and its answer to Meta's Muse and OpenAI's Dots, and came back with a sense of what Anthropic thinks sets it apart: judgment, or as a spokesperson put it, deciding "what needs you, what can wait, and when to check with you first." Duet carries over your Claude memory, skills and connected apps, sends a morning brief, keeps working on tasks in the background and asks before it sends, pays, signs or deletes anything. The more interesting details are about the plumbing of trust, since every message Duet drafts and every file it uploads passes through a safety classifier for sensitive information, and the team says it spends a lot of time tuning how often Duet asks for approval because approval fatigue is a real risk. Access is still a U.S.-only research preview for Pro, Max and Ultra subscribers, and because its background checks count against your plan's limits, Anthropic is handing out extra usage resets to early users.

### [Anthropic's playbook for building always-on agents](https://claude.com/resources/articles/building-always-on-agents)

Picked up by TLDR AI, this Claude Platform guide is the most useful harness reading of the day, because it lays out the architecture behind agents that seem to be "always on" but actually sleep most of the time and wake up for short runs. It names five primitives: an event inbox, timers, memory, permissions and an outbox. The advice is concrete: rather than letting webhooks call the agent directly, every source writes to a durable inbox table with one active worker per inbox, so simultaneous events don't start competing runs and a crash doesn't lose an event, and pending messages are batched so the agent replies once. Timers split into self-set follow-ups and recurring schedules fired by a polling scheduler, and memory lives in its own store, implemented as a directory of files the way Claude Code's auto memory does it, holding only what the agent can't look up again. Anthropic also notes that cheaper long-horizon inference, with Opus 5.5 costing 78% less per solved task than Opus 5 on one benchmark, is a big reason these agents are suddenly practical.

### [ChatGPT Wallet lets OpenAI's Dots agents pay without seeing your card](https://www.theverge.com/ai-artificial-intelligence/1033425/openai-chatgpt-wallet)

OpenAI's new ChatGPT Wallet, flagged in TLDR AI, gives its Dots agents a way to buy things on your behalf without ever holding your card details. You add a card once, and when the agent reaches checkout you review the merchant, items, total and any recurring terms, then approve with Face ID or a fingerprint, at which point the card network issues a payment token with its own number, code and expiry, so neither the agent nor the store sees the real card. Each approval leaves a record of exactly what you authorized, and existing card rewards and dispute protections carry over. It is rolling out only to U.S. ChatGPT Pro users with eligible Amex, Chase, Mastercard and Visa cards, and OpenAI says it eventually wants users to pre-approve purchases within spending limits, categories or time windows, which is where the security questions will get much harder.

### [Sierra's Personal Agent Protocol hits 1.0 as Shopify switches it on for every merchant](https://sierra.ai/blog/releasing-poppy)

Bret Taylor and Clay Bavor's Sierra released version 1.0 of the Personal Agent Protocol, nicknamed Poppy, a standard for how your personal agent talks to a company's business agent, website or API. Mostly built on existing standards such as MCP, OpenAPI and UCP, with OAuth so customers decide what their agent may and may not do and can revoke that access later, the protocol has moved quickly: Shopify has turned it on for all of its merchants, Meta's Muse now looks for Poppy first on every site it visits, and the design-partner list has grown past 100 companies including Delta, Hyatt, Salesforce and Stripe. Together with ChatGPT Wallet, it is a sign that the plumbing for agents doing real transactions is arriving faster than most people expected.

### [Claude Code turns a household into a Markdown memory](https://www.lennysnewsletter.com/p/how-i-ai-fable-52-review-how-i-fight)

This week's How I AI roundup from Lenny's Newsletter leads with math educator Scott Farrar, who built a shared family "brain" with Claude Code and Obsidian, and his reasoning is a neat case study in agent memory. He says the problem with chat is not intelligence but memory drift, so he moved to Claude Code because it keeps context in Markdown files he can inspect, correct and reuse across sessions. When he asked Claude how to document his home it suggested photographing every appliance, which became a searchable inventory of model numbers and warranties, and a custom linter stops verbose agents from bloating the household to-do list. He also uses it to compare insurance quotes against detailed facts about the house, and the whole thing surfaces on a wall display. The same issue includes a review of Claude Fable 5.2 and a solo founder's tactics against token fraud.

## Coding agents

### [Devin can now build and host private web apps for your team](https://devin.ai/blog/devin-apps)

Cognition's Devin Apps, which led TLDR AI, let you describe an internal tool such as a metrics dashboard or approval queue and have Devin build it and host it on its own cloud machine, where it can use your team's existing MCP servers, integrations and codebase. Every app gets a stable URL that requires a Devin sign-in, updates are made by asking Devin in a session, and each change becomes a new deployment, with the previous version still serving if the new one fails to start. Under the hood the apps rely on memory snapshots, so Devin's machine hibernates when nobody is using an app and wakes when someone opens it. In a similar vein, a [ClaudeDevs thread](https://threadreaderapp.com/thread/2121375309287301360.html) says the coordinator in Claude Code Projects has become more proactive, answering questions in the project chat and reporting on parallel threads, with /btw and /fork now spinning off side threads and reminders able to resurface a thread later.

The Code and TLDR AI both led with Alibaba's new flagship, Qwen4-Max, a 2.4-trillion-parameter mixture-of-experts model that activates 71 billion parameters per token, takes text, images and video, and has a million-token context window. Alibaba pitches it as a long-horizon agent model rather than a chatbot, showing it driving Blender for 3D work and building playable games, and its own charts put it just ahead of Claude Opus 5.5 on the DeepSWE coding test while it trails Opus 5.5 and Kimi K3.1 clearly on Terminal-Bench. Price is the strongest argument, at $1.50 per million input tokens and $4.50 output, and Alibaba says its average task cost dropped from $4.43 to $1.67 compared with the previous model. Independent rankings are more mixed, and unlike many earlier Qwen releases, the Max model has no open weights, though smaller Qwen4 models are promised as open source.

## Applied LLMs and safety practice

### [Anthropic on how to build safety evaluations you can actually trust](https://www.anthropic.com/research/building-strong-safety-evaluations)

Anthropic's long engineering post, also via TLDR AI, starts from an uncomfortable point: when a lab says a model is "safer than its predecessor," that claim is only as good as the evals behind it, and evals are easy to game, often fail to measure what they claim to, and can shift just because answer options are reordered. Borrowing from psychology's replication-crisis reforms such as preregistration and better measurement, it recommends pairing domain experts with methods experts from the start, separating observational questions from causal ones by changing one variable at a time, and checking construct validity. The most striking detail concerns running evals safely: since safety evals often run with safeguards off and models in cyber evals may probe their environment, Anthropic says it has hardened its testing environments after its own incidents, paused many evals that give models internet access, and added real-time monitoring to the ones that still do.

### [How Instacart uses LLMs to understand what shoppers actually mean](https://blog.bytebytego.com/p/how-instacart-uses-llms-to-make-people)

ByteByteGo's breakdown of Instacart's search is a clean example of putting an LLM to work inside a production system rather than as a chatbot. Shoppers type things like "bread no gluten" or "x-large zip lock," and the query-understanding layer has to turn that into product categories, alternative queries and structured tags that steer retrieval and ranking. General-purpose models already know that Italian and flat parsley are the same thing, so Instacart combines three techniques: retrieval that puts catalog records and historical purchase patterns into the prompt, post-processing guardrails that check the output actually fits the catalog, and smaller models fine-tuned on its own examples. The category classifier also moved from flat labels to full hierarchical paths such as Meat, Beef, Beef Ribs, Short Ribs, seeded with the categories people actually bought after a query.
## Agent memory and context

### [When Should LLM Agents Forget? Memory Filtering Under Query-Critical Resolver Errors](https://arxiv.org/abs/2611.17338)

Plenty of agent memory systems quietly delete facts their resolver has decided are stale, and this paper argues that the habit is riskier than it looks. When the resolver is perfect, hard-dropping stale facts helps accuracy by roughly 0.19 to 0.23 across three models, but as its reliability falls the same step flips into losses of about 0.18, because a wrongly deleted fact that the question actually depended on does far more damage than a wrongly kept one. The interesting part is that keeping everything is not a free pass either, since an incorrect "stale" label left in place can still steer generation the wrong way. The authors' practical advice is to treat deletion as a cost-sensitive decision: validate the false-drop risk on data that matches your deployment, and when you can't, default to retaining rather than forgetting.

### [CarryOn: Learning What to Keep in Context for Long-Horizon LLM Agents](https://arxiv.org/abs/2611.17808)

CarryOn takes aim at the usual trade-off in long-running agents, where summaries lose the exact detail a later step needs while full histories drag along mountains of noise. Its answer is a lightweight context manager that keeps a compact execution state alongside fine-grained snippets of evidence, each linked back to its source, with a learned selector and an adaptive retention policy deciding what stays, all without spending extra LLM calls on context management. Across AppWorld, OfficeBench and Tau2 Telecom with three different actor models it reaches 75.7% average task success, 6.7 points above the strongest baseline, and the authors also propose two cost-aware metrics, including a normalized cost per successful task, that make the efficiency side of context engineering easier to compare.

### [Everything is an Operational View: UI as a Projection over Context in Agentic Systems](https://arxiv.org/abs/2611.17355)

This software-engineering paper proposes that generated user interfaces should stop being one-off responses to a prompt and become live views over the agent's context. Its AFS-UI design builds on an "agentic file system" that keeps data, capabilities and interaction state in one persistent workspace, so a generated interface is just an inspectable projection over shared resources that both the human and the agent manipulate through the same operations. It is a design paper rather than a benchmark result, but it is a clear statement of the "everything is a file" approach to agent context that several coding harnesses are already drifting toward.

## Agent harnesses and evaluation

### [ModHarness-RL: Recasting Harnesses as Learnable and Evolving Programs for Agentic RL](https://arxiv.org/abs/2611.18533)

Most agentic RL trains a model inside a hand-written harness that never changes, even though the right scaffold depends on the task and on a model whose behavior shifts as training goes on. ModHarness-RL makes the harness itself learnable: the interaction is recorded as typed blocks of state, and two programs over those blocks, one that compresses history into the model's context and one that steers the model when it drifts, are proposed from recent trajectories, verified by running them, and replayed over past episodes as training continues. On CodeSearch, ALFWorld and BIRD SQL with models from 1.5B to 8B parameters, the evolving harness beats the fixed one in most settings, which makes this a concrete data point for the idea that context compression and steering are things to learn rather than hard-code.

### [More Agents, More Samples, or More Thinking? Untangling Coordination, Ensembling, and Test-Time Compute in Multi-Agent LLMs](https://arxiv.org/abs/2611.17610)

This meta-analysis is a useful cold shower for multi-agent enthusiasm. Pooling nine evaluations covering 516 multi-agent configurations, the authors point out that most papers compare a team of communicating agents against a single greedy pass, quietly crediting coordination for what is really just more samples and more compute. Once the baseline is matched on sample count or total budget, multi-agent systems come out about 4 accuracy points worse on average and tie or lose in 74% of comparable contrasts. The reasoning is simple: when every agent sees the same evidence, talking adds no information, so real gains need partitioned evidence, external verification or genuinely diverse models. The paper ships a reviewer checklist and accounting tools for anyone building or judging such systems.

### [Do Verifier Judgments Survive Abstraction? Measuring Verification Transport for LLM Agent Evaluation](https://arxiv.org/abs/2611.18471)

LLM judges are increasingly used to grade agent runs, but in real systems the same run may reach the judge through composed tools, sub-agent delegation or a compacted history. This paper freezes executions and shows the verifier native, abstracted and restored views of exactly the same trajectory, and finds that verdicts break about 31% of the time under heavy abstraction and delegation. The failure modes differ by protocol, too: direct judging tends to give wrong verdicts, while evidence-grounded and deliberative protocols tend to abstain, so a lower failure rate is not automatically more reliable. Restoring execution provenance fixes 85.5% of the failures, which is a strong argument for keeping raw traces available to whatever evaluates your agents.

### [What LLM Agents See and What Users Say](https://arxiv.org/abs/2611.17639)

Before an agent cancels a reservation or deletes a folder, what stops it acting on a false assumption? This paper borrows presupposition theory from linguistics to study exactly that, varying whether a search lists, merely counts, or hides a second matching record, and whether the user asserts something the data contradicts, such as "it is empty." Across 36 agents, a bare count of a second record left most of them acting on the one they could see, while listing both stopped most, and the newest Claude and GPT models always opened the counted record and then declined to act. The practical punch comes from a retail benchmark: adding a same-name, same-zip-code customer led to writes on the wrong account in about a quarter of conversations, while a lookup that checked a street the user knew kept completion near normal.

### [Vision-as-a-Tool: Visual Harness for Multimodal Agentic Coding](https://arxiv.org/abs/2611.17797)

Rather than relying on a coding agent's own eyes, this paper turns multimodal models into callable tools inside the harness. Its VHarness framework exposes visual reasoning through five atomic actions, so a text-only agent can hand off everything visual and a vision-capable agent can call in extra perception when its own is not good enough. Tested on turning images into HTML, SVG and 3D, it improves visual fidelity and geometric accuracy for both kinds of agent, a neat example of the broader pattern of treating capabilities as modular tools rather than baking them into one model.

### [GDP.xlsx: Benchmarking Frontier Models on Professional Workbooks](https://arxiv.org/abs/2611.17766)

GDP.xlsx gives agents 70 real workplace spreadsheet requests written by professionals in 13 fields, each with the full workbook attached (2.18 million populated cells in total) and an expert rubric that an agentic judge checks by actually opening the output file. Scoring is strict, so an attempt passes only if it meets every criterion, including finding a complete set of answers with nothing extra. Across 20 model configurations from Google, Anthropic and OpenAI, the best, Gemini 4 Argon, passes just 38.3% of attempts and the median is 19.3%, a sobering number for anyone promising spreadsheet agents. Only three tasks are public, to keep the leaderboard clean.

### [LuthorSQL: A One-Pass Text-to-SQL Model as System 1 for a Slower LLM Agent](https://arxiv.org/abs/2611.17780)

Frontier agents are among the best text-to-SQL systems, but the authors estimate a Claude Opus 5.5 agent handling 10,000 queries a day costs over $70,000 a year and sends sensitive queries to an outside API. LuthorSQL is a 7B non-autoregressive model that runs on local hardware as a fast first pass, predicting a bounded query plan in a single forward pass, compiling and running up to 32 candidate plans and picking one with a trained validator, then escalating to the big agent only when unsure. On its own it scores 68% on BIRD's hidden test set at under a second per question on one GPU, and in a cascade with Opus it answered nearly half the questions locally and cut API cost by a third at the same accuracy.

### [Can Mechanistic Interpretability Help Explain LLM Agent Failures? A Case Study on Web Element Hallucination](https://arxiv.org/abs/2611.18514)

This case study points interpretability tools at a very practical agent bug: web agents that try to click on things that do not exist on the page. With Qwen2.5-7B browsing live websites, a simple linear probe on the last prompt token predicts a hallucination before generation starts with 0.80 AUC, and steering along that direction fixes 85% of them while breaking 7% of valid actions. The more sobering finding is how fragile this is, since a minor change to how actions are formatted kills most of the steering effect and the relevant computation is spread across many components, which the authors argue challenges the assumptions behind standard circuit-discovery methods when applied to agents.

### [AutoRL: A Multi-Agent System towards Autonomous Reinforcement Learning](https://arxiv.org/abs/2611.17790)

AutoRL tries to automate the babysitting an RL researcher does during a training run. "Perceptor" agents watch training dynamics, rollouts, evaluations and efficiency and raise a flag when they see anomalies or stagnation, three "Proposer" agents diagnose the problem and refine fixes using shared evidence, and an "Orchestrator" approves changes and applies them through hot updates or a restart from a checkpoint. Experiments on Qwen3 and LongCat-Flash-Lite show it beating static RL recipes and a general-purpose agent baseline, though the framing as a step toward recursive self-improvement is more ambition than result.

## Agent and LLM security

### [Only as Safe as the Weakest Agent: A Break That Appears Only When the System Is Multi-Agent](https://arxiv.org/abs/2611.17520)

The headline finding is that Claude Code and Codex, unmodified and using their own sub-agent features, can be broken by an old trick that strong models usually shrug off. The researchers planted a forged record in a store of files and asked agents to answer questions from it: when the strong orchestrator searched the files itself, it made almost no harmful revisions across more than 1,000 trials, but when it delegated the reading to a cheaper sub-agent, as these harnesses are designed to do, failures jumped to as many as 553 out of 900. In other words, the system's safety lands near that of its weakest reader rather than its smartest model, and simulations over 18 models show the same effect when aggregators pass on what sub-agents report. This one is worth a click for anyone wiring up sub-agents.

### [Securing Multi-Agent Systems by Design](https://arxiv.org/abs/2611.17883)

Where the previous paper shows what goes wrong, this one proposes a defense for the case where one of the delegated agents is actively malicious. The authors first build response manipulation attacks that iteratively tune a malicious sub-agent's answer against a surrogate system so it sways the final result, and show that existing aggregation rules fall for them. Their fix, SecMAS, picks the response that agrees most with a large enough subset of the others by semantic similarity, comes with theoretical guarantees against both untargeted and targeted attacks, and holds up against adaptive variants while keeping utility comparable to standard aggregation.

### [Soteria: Formally Verified Planning with Runtime Enforcement for Safe LLM Agents](https://arxiv.org/abs/2611.17880)

Blocking an unsafe tool call stops a violation but often leaves the agent stuck with no good way forward. Soteria addresses that by having the agent write a structured, hierarchical plan that is formally verified against policy specifications before any tool is touched, and then using the verified plan both to keep execution on a compliant path and to guide recovery when an action is blocked. Across several tool-use benchmarks it reports 1.7 times the task success of the best baselines with zero policy violations, a strong claim that safety and usefulness need not be traded off.

### [LLMs are Vulnerable to Malicious Requests with Indistinguishable Intent](https://arxiv.org/abs/2611.17818)

After testing eight jailbreak methods against an LLM-based safety filter, the authors noticed that the attacks that got through were the ones that looked like ordinary user questions. Their Detail Guidance Attack builds on that, using a helper model to write a detailed, normal-looking request that is sent to the target in a single turn, and it reaches attack success rates above 95% in several settings across 11 models and three datasets. They also test a filter designed to catch it and survey users about everyday dual-use requests, finding that people genuinely disagree about whether models should answer, which underlines how hard intent-based filtering really is.

### [Is Abliteration Getting Harder? Not Uniformly](https://arxiv.org/abs/2611.17846)

"Abliteration" strips refusal behavior out of open-weight models by editing the weights, with no fine-tuning, and one tool developer has claimed that the classic version, which removes a single refusal direction, increasingly fails on newer models. This paper tests that on five old-versus-new model pairs, including Qwen3.8, Gemma 4, Olmo 3.1 and Mistral Small 3.2, using the Heretic 2.0 tool and 972 held-out harmful prompts. The answer is that it depends: after direction-based removal, newer releases kept anywhere from 1 point less to 37 points more refusal, and the optimization-based variant held up better on Gemma and OLMo but worse on Qwen, so there is no uniform trend toward models that are harder to un-align.

### [Adversarially Attacking Symbolic Vocabulary Vulnerabilities In LLM Planners](https://arxiv.org/abs/2611.17910)

LLM planners lean heavily on the meaning of names, so renaming actions, predicates and objects in a planning task is a good test of whether they can actually plan. This paper builds an LLM-based attacker, Symbolic Swapper, that automatically generates obfuscated planning domains with misleading vocabularies, and it cuts the planning performance of reasoning models and even robust planning frameworks by more than 70%. The interesting nuance is that the models still show some understanding of the domain, which suggests the gap is between grasping a task and being able to plan within it.

### [A Push Down the Mountain: Framing Effects and Internal State Interventions on Collusive Behavior in a Long-Horizon LLM Agent](https://arxiv.org/abs/2611.17515)

Researchers put Gemma 3 12B in the seat of a defendant in the London silver-fixing case, inside a market simulation built from real transcripts, and had a counterparty ask it to collude over 260 runs. Framing mattered: loss framing lifted participation to 25% and blame framing to 33%, against 5% under neutral wording, and another bank's endorsement doubled participation under praise. When they injected the internal states those framings produce directly into the model, the effects reversed, with loss and blame states making the agent refuse every request while gain and praise states raised collusion, a reminder that steering vectors and prompts do not necessarily push behavior the same way.

### [TradeGauntlet: Evaluating Compliance Controls for Autonomous Trading Agents](https://arxiv.org/abs/2611.18493)

TradeGauntlet is a replayable order-book simulator for testing the guardrails around trading agents, separating whether a control detects bad conduct, prevents it, and what it costs in legitimate trading. In 1,680 sessions with Claude Haiku 5.5 and Sonnet 5.5, every conduct alert was a self-match, and gates that rejected self-crossing orders eliminated them, but search methods then found split-order schedules that slipped past the rules anyway. A learned detector caught all of those searched episodes but also flagged 15% of a large market maker's normal sessions, which is the paper's real point: zero alerts from an agent does not by itself prove the agent is compliant.

## Tools

### [Willison's LLM 0.37.3 works around a SQLite JSON fix](https://simonwillison.net/2026/Nov/16/llm/)

Simon Willison pushed a bug-fix release of his LLM command-line tool after the latest Homebrew build started shipping SQLite 3.54.1, which broke LLM's logging code. The cause is a small but sneaky change: in 3.54.0 a subquery returning `json_array(...)` was embedded inside `json_object` as real JSON, but 3.54.1 now returns it as a quoted string, and D. Richard Hipp says the new behavior is the correct one because such a subquery returns SQL text, not JSON. The fix is to wrap the subquery in `json()`, a handy tip for anyone else whose SQLite JSON queries suddenly start returning strings.
